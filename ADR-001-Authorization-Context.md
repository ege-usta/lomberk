# ADR 001: Separation of Control Plane and Execution Capability

## Context
The previous architecture used a single `mcp_agent` DB role for both control operations (creating checkpoints, changing states) and executing DML. The capability token (`exec_token`) was generated by `claim_checkpoint` based purely on the `public_id`. Since `public_id` is exposed to the agent (e.g., in `approval_required` responses), the agent could maliciously claim and execute unapproved checkpoints, bypass approvals, or spoof context.

## Decision
We implement a strict Separation of Duties and Capability-Based Execution:
1. **Roles Matrix**:
   - `lomberk_control` (Trusted API/System): Has `EXECUTE` on control plane functions (`begin`, `approve`, `reject`, `fail`).
   - `mcp_agent` (Untrusted Runtime): Has `EXECUTE` ONLY on `claim_checkpoint` and `finish_checkpoint`, and raw DML access to registered tables.
2. **State & Capability Generation**:
   - Checkpoints start as `pending`. Runtime cannot change this state.
   - The control plane explicitly transitions to `approved` via `approve_checkpoint(public_id)`. This function generates a cryptographically secure, single-use `capability_token` (UUID).
   - The API securely holds this token and passes it to the executor for the specific transaction.
3. **Execution Context Binding (Transaction Isolation)**:
   - The runtime begins an explicit transaction (`BEGIN`).
   - `claim_checkpoint(capability_token)` is called. It verifies the token, transitions state to `executing`, and irreversibly binds the checkpoint to the current transaction ID (`exec_txid = txid_current()`).
   - The runtime sets `lomberk.capability_token` in the local GUC.
   - `capture_row_change` trigger enforces that the GUC matches the DB, the status is `executing`, AND the `exec_txid` precisely matches the caller's `txid_current()`.
   - `finish_checkpoint(capability_token)` also asserts `txid_current()` before committing.
   - Any failure or rollback destroys the `claim` mutation (due to MVCC), meaning the checkpoint remains `approved` but the transaction is lost. The control plane can explicitly transition it to `failed` using `fail_checkpoint`.

## Consequences
- **Spoofing Prevention**: A compromised `mcp_agent` cannot approve its own checkpoints or steal another's, because it lacks DB grants for control functions and cannot guess the `capability_token`.
- **Replay/Stealing Prevention**: Even if `capability_token` is intercepted in memory, it is mathematically bound to a specific PostgreSQL transaction (`txid_current()`). Another backend or transaction using the same token will fail the `exec_txid` validation.
- **Atomicity**: The entire claim->DML->finish sequence happens in a single explicit transaction.
