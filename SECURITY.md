# Security Model

Lomberk sits between AI agents and PostgreSQL. This document states what it defends against, how, and what it does **not** cover, so a security team can evaluate it honestly.

## Reporting a vulnerability

Please use GitHub's **private vulnerability reporting** ("Security" tab → "Report a vulnerability") on this repository. Do not open public issues for security problems.

## Trust boundaries

| Actor | Holds | Can |
|---|---|---|
| AI agent | gateway URL + **agent key** only | submit SQL to `/mcp` or `/v1/execute` |
| Gateway service | control DSN, agent DSN, both keys | classify, hold, execute, undo |
| Human approver | **admin key**, SSO identity or Slack allowlist | list, approve, reject, undo (API, CLI, Slack, web panel) |
| DB owner / installer | install DSN (used once) | install schema, register tables |

The agent never receives a database credential or the admin key. **Deploy the gateway as its own service** (see `Dockerfile` / `docker-compose.yml`). The stdio mode (`lomberk serve`) puts DSNs on the agent's machine and is meant for local development only: an agent with shell access there can approve its own requests.

## Defenses

1. **AST hard gate** (PostgreSQL's own parser via `pglast`): exactly one statement; only `SELECT/INSERT/UPDATE/DELETE` and plain `EXPLAIN` (never `EXPLAIN ANALYZE`, which runs the statement); writes must be schema-qualified and have a `WHERE`; functions limited to an allowlist of pure built-ins (`ALLOWED_FUNCS` in `sentinel.py`: aggregates, window, text, date, math, array and JSON functions agents use every day). Left out on purpose: anything that can run a SQL string (`query_to_xml`), ask for a gigabyte in one call (`repeat`, `lpad`, `format`'s width), or list every value of a JSON column without naming a key (`jsonb_each*`, `jsonb_path_*`). Blocks DDL, `SET`/`RESET`, `COPY`, `DO`, `PREPARE`, `CALL`, `LOCK`, `SELECT INTO`, `set_config`/`current_setting`, `pg_*`, `dblink`, `lo_*`, `nextval`, and stacked statements. System catalogs (`pg_catalog`, any `pg_*` name, and information_schema's user-mapping views) can't be read, because `pg_stats` keeps sampled column values and `pg_proc` keeps function source. `information_schema` stays readable for schema discovery. SQL containing invisible text-direction characters (Trojan Source) is refused, so the approver reads the same SQL that runs. See `tests/unit/test_firewall_attacks.py`; `tests/unit/test_firewall_usability.py` holds the other half of the contract, everyday agent SQL that must pass.
2. **Policy**: protected tables (`schema.table`; a bare name fails startup, because it would protect nothing) and a per-statement row limit. Writes are executed inside a transaction; if they exceed `limits.max_rows_without_approval` **or can cascade (via foreign keys) into a protected table**, they are rolled back and queued for approval. `WHERE 1=1` tricks are caught by the row count, not by pattern matching.
3. **Database-enforced capture**: a `SECURITY DEFINER` trigger records every changed row, including FK cascades. It refuses agent-role writes that are not bound to a live, single-use capability token for the current transaction. Writes whose cascade would reach an unregistered table are refused, because those rows could not be undone.
4. **Least privilege**: startup refuses superuser roles and refuses when the control and agent DSNs resolve to the same role. The agent role only gets DML on registered tables.
5. **Approvals**: human-only (OIDC SSO, admin key, CLI, or Slack allowlist), constant-time key comparison, expiry after `agent.approval_timeout_minutes`, with the hard gate re-checked at approval time. Held writes are dry-run for the approval preview (`approvals.preview`, on by default): the write executes inside its capability-bound transaction, `lomberk.preview_changes` reads the rows it captured (only with that transaction's live token, and only columns the agent role may SELECT), and the transaction is rolled back before anything commits. Preview values are shown escaped (text-direction characters as `\u202e`) and cut at 200 characters. At approval the write runs again and must change exactly the rows the approver saw (row count and a digest of table, operation and key); if the data or the clock moved, it fails and nothing is changed. A write held for the row limit or a protected cascade keeps that row count and digest even with `approvals.preview: false`. Writes to tables with their own triggers, or that can cascade into one, are not dry-run; neither are policy holds when `approvals.preview` is off. Those run at approval against the data as it is then, with no row cap, so the approver is approving the SQL text. A dry run costs what the write costs, and its error, if any, reaches the agent like any failed write's. Sequences a dry run advances are not rewound, as with any rolled-back write.
   Every approval is recorded in the append-only `lomberk.approvals` table, which only a `SECURITY DEFINER` function can write. With `approvals.required: N`, a held write runs only after N distinct identities from one verified system (OIDC or Slack) approve it, under a row lock so concurrent approvers can't race it through. The shared admin key and CLI users can't make up a quorum, and neither can one person's SSO plus Slack identities. One reject cancels the write.
   Slack: the bot has only the `chat:write` scope and uses Socket Mode (no inbound URL). A click counts only when the team and user are allowlisted **and** the `(team, channel, message_ts)` matches the durable binding the gateway recorded when it posted. The checkpoint ID in the button is never trusted on its own. A post whose outcome is unknown is never re-sent, and SQL is not sent to Slack unless `slack.include_sql` is set.
6. **Undo**: undoes rows in an order that respects foreign keys. It refuses when a row changed after the checkpoint, when the schema drifted, or when the undo would cascade into rows it did not create. It also refuses (`expired`, nothing changed) a checkpoint older than the plan's undo window: 24 hours free, 30 days Pro, no limit Enterprise, counted from when the write ran. The window is a plan limit, not a security boundary: the captured rows stay in `lomberk.row_changes` either way.
7. **Tamper-evident ledger**: checkpoints are append-only (UPDATE/DELETE of recorded fields is blocked) and SHA-256 hash-chained. `lomberk verify-ledger` finds the first altered entry and prints the head hash.
8. **Web panel** (Pro, `/panel`): the session is an HMAC-signed, HttpOnly, SameSite=Strict cookie keyed from a random secret made at each gateway start, not from the admin key, so holding the admin key can't forge a session (or an `oidc:` approver). A restart signs everyone out, and with several gateway replicas a session works only on the replica that issued it (use sticky sessions). An admin-key session lasts 8 hours. An SSO session ends when the IdP's ID token expires (usually 1 hour), and every request re-checks today's `allowed_identities` / `allowed_groups`, so removing a person or group from the config signs them out at once. Every state change also needs a custom header that a cross-site form can't send. The panel uses a strict CSP (no inline or third-party script, no framing) and renders agent SQL as text only. SSO sign-in uses the OIDC authorization code flow with PKCE, `state` and `nonce`, done server side, and the resulting ID token passes the same checks as API approvals.
9. **License check** (only with a key): HTTPS calls to `api.polar.sh` at startup that send the license key and, for a Pro key that covers a fixed number of databases, a random label for this database (`lomberk.license_activation`, no host or database name). `lomberk undo` makes the same check only for a checkpoint older than 24 hours. No SQL, rows or usage data leave. If Polar is down (no answer, or a 5xx or 429 reply, three tries), the paid plan stays on, so blocking that host doesn't break the gateway. Any other reply that isn't a valid grant for a Lomberk benefit is treated as an invalid key (fail closed). The key is checked at startup only, so a revoked key turns paid features off at the next restart.
10. **Data minimisation**: columns whose names contain `password`, `passwd`, `pwd`, `token`, `secret`, `ssn`, `hash`, `credit_card`, `api_key`, `apikey`, `private_key` or `credential` can't be referenced, named as a JSON key in an operator or a function argument (`->>'api_key'`, `@? '$.api_key'`, `strpos(settings::text, 'token')`, `'api_' || 'key'`), renamed, read as part of a whole row (`u`, `u::text`, `jsonb_build_object('r', u)`), or reached through `*` inside a subquery, CTE, `UNION` or `INSERT ... SELECT`. A top-level `*` masks them in results, and next to a `*` the query can't sort or group by column number or use `NATURAL JOIN` (both would compare a masked column without naming it). Errors returned to the agent carry PostgreSQL's message only, never its DETAIL, which for NOT NULL and CHECK violations prints the whole row. See `tests/unit/test_sensitive_columns.py`. The audit log is owner-only (`0600`) and never written to `/tmp`.

## Residual risks (known, documented)

- **Database superusers** can disable triggers and rewrite the whole hash chain. Export the `verify-ledger` head hash to an external system (SIEM, WORM storage) to detect this.
- **Read access** is governed by the agent role's grants. Secret columns are found by name: the built-in keywords plus the names you list in `sensitive_columns` (use it for `pass`, `pin`, or a JSON column that holds secrets). `lomberk register` hides them with PostgreSQL column privileges, so on registered tables the database itself refuses them, whatever the SQL. Inside JSON, secret-looking keys are masked and can't be queried by name, and JSON keys and array positions must be written as literals (`->>'theme'`, `->0`), not computed at run time. This is best effort: casting the column to text (`' ' || settings::text`) still returns the whole document, and JSON can hold a secret under any key. `sensitive_columns` is the boundary: list every JSON column that may hold a secret there, and the database refuses it outright. Tables the agent reads but you didn't register keep your own grants; `lomberk doctor` lists every secret-looking, suspicious or JSON column the agent role can read, so none goes unnoticed.
- **Sequences are not rewound** by undo, which is intentional (ADR-005).
- **Undo scope**: tables need a primary key, single or multi-column; it is checked when the table is registered, and undo refuses if it changed shape since. Declarative partitioning is supported when every partition is a plain table carrying the cloned capture trigger, with no rules and no triggers of its own (checked before each write and again at undo); a partition can't be registered or written to on its own, and registration takes away any grant the agent role had on the partitions. A write that can cascade into a table with its own triggers waits for a person, because undo couldn't restore that table. Agent writes to tables with rewrite rules or classic inheritance are refused before they run, because some rows would bypass capture. A write to a table with its own triggers (e.g. `updated_at`) waits for a person, who sees why, unless the owner registered the table with `--allow-triggers`. Then undo switches those triggers off inside its own transaction (they come back at commit or on any error), so restored rows match exactly and nothing fires twice. That flag is the owner's promise that the triggers only touch the row itself or registered tables: a trigger that writes to an unregistered table leaves that write in place after undo. Only the role that installed Lomberk, if it owns the table, can set it. Identity and generated columns are supported. DDL is blocked, not reversible.
- **TLS** is not terminated by the gateway. Run it behind a TLS reverse proxy or service mesh.
- **Optional LLM sentinel** (`OPENAI_API_KEY`) sends SQL text to a third party and is advisory only. Leave it unset if SQL may contain regulated data.
- **Throughput**: checkpoint creation is serialized by one ledger lock.
- **Key guessing**: the gateway refuses to start with a key shorter than 32 characters, a public demo key or an obviously repeated one (`LOMBERK_ALLOW_WEAK_KEYS=true` is for laptop demos only), so guessing a key is not feasible. A proxy rate limit is still good hygiene.
- **IdP removals**: someone removed at the IdP (not in the config) keeps a panel session until their ID token expires, usually 1 hour, the same as any OIDC app. For an instant cut, remove them from `sso.allowed_identities` / `allowed_groups` and restart.
- **Approver identity**: with `sso` configured (Pro), API approvals carry the person from a verified OIDC ID token, and the shared key is off unless `sso.allow_admin_key: true`. An approver allowlist (groups or identities) is mandatory. Without it, API approvals are the shared admin key and CLI approvals are the OS user. Slack approvals always carry the Slack user ID.

## Hardening checklist

- [ ] Gateway runs as a separate service; agents get only the URL + agent key.
- [ ] Keys are 32+ random characters (`openssl rand -hex 32`), distinct, and rotated; held in a secret manager. `LOMBERK_ALLOW_WEAK_KEYS` is unset.
- [ ] Secret columns the keyword list can't guess are in `sensitive_columns`, and every agent table was registered after that; `lomberk doctor` shows no readable secret column.
- [ ] The TLS proxy sends `X-Forwarded-Proto: https`, so panel cookies are always marked Secure.
- [ ] TLS in front of the gateway; `/v1/checkpoints/*`, `/v1/audit/*` and `/panel` reachable only from approver networks, rate-limited at the proxy.
- [ ] Every table the agent may write is registered (`lomberk register`), including FK children.
- [ ] `protected_tables` and `limits.max_rows_without_approval` reviewed. Config typos fail startup by design. Set `LOMBERK_CONFIG` to the file's absolute path: if it is missing, startup is refused, whereas a missing `./lomberk.yaml` only warns and protects nothing.
- [ ] `verify-ledger` head hash exported on a schedule; audit log shipped to your SIEM.
